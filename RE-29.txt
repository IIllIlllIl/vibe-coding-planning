## 文档版本信息

|------|------|------|----------|

## 1. 项目概述

### 1.1 项目背景

当前，基于大语言模型的代码生成智能体（Agent）已在软件工程任务中展现出巨大潜力。然而，现有工作普遍采用“一步到位”的代码生成范式——Agent直接根据用户需求生成代码并通过测试评估。这一模式忽略了软件开发中的关键环节：**方案规划**。

在实际开发流程中，经验丰富的工程师在动手编写代码前，会先设计方案，明确技术路线、模块划分和依赖关系，再按方案落地代码。类似地，Claude Code CLI 的 Plan Mode 等产品已证明，要求 Agent 在代码生成前先给出详细方案，能够显著提升代码质量和任务完成率。

与此同时，**方案的迭代优化**是软件开发能力的核心体现。一次规划难以完美，根据执行反馈持续改进方案，既是开发者提升效率的关键，也是自动化系统实现自我增强的必经之路。

本项目旨在构建一套**自动化的方案评估与迭代优化系统**，以 SWE-bench 为评估基准，以 DeepSeek V4 为底层模型，通过 Agent 自主探索代码库并生成方案，执行代码生成与测试评估，再基于执行反馈迭代优化方案，最终输出多个方案及其对应的测试通过率，为研发团队提供可量化的方案评估依据和可复用的优化经验。

### 1.2 项目目标

| 目标编号 | 目标描述 | 优先级 | 衡量标准 |
|----------|----------|--------|----------|
| G-01 | 实现基于 Agent 的自动化方案生成与评估流程，输入 Prompt 后自动输出至少一个方案及测试结果 | P0 | 系统能够完成单轮方案生成→代码生成→测试评估全流程 |
| G-02 | 实现方案的迭代优化能力，能够基于执行反馈生成后续方案 | P0 | 当参数 n > 1 时，系统能够产生 n 个方案，后序方案基于前序方案优化生成 |
| G-03 | 支持灵活配置优化信息，可选择是否包含测试运行结果和报错信息 | P1 | 可通过配置文件开关控制是否将测试结果纳入优化信息来源 |
| G-04 | 最小化开发工作量，优先复用现有开源工具（KISS AI、GEPA 等） | P0 | 核心功能基于 KISS AI 框架和 GEPA 算法实现，仅需少量填充代码 |
| G-05 | 在 SWE-bench 数据集上验证系统有效性 | P1 | 能够在至少 10 个 SWE-bench 实例上完成端到端运行 |

### 1.3 系统范围

#### 包含范围
- 自动加载 SWE-bench 数据集中的任务（代码库 + Issue 描述）
- Agent 在代码库环境中自主探索并生成代码方案（Plan）
- 根据方案驱动 Agent 生成可执行代码（Patch）
- 在 Docker 容器化环境中运行测试评估 Patch 有效性
- 基于执行反馈（Agent 轨迹、代码、测试结果等）迭代优化方案
- 输出多个方案及其对应的测试通过率，记录每次优化的思路

#### 不包含范围
- 训练或微调新的 LLM 模型
- 构建新的代码测试环境或修改 SWE-bench 评估框架
- 支持 SWE-bench 以外的数据集（作为后续扩展）
- 提供 Web UI 或图形化界面（作为后续扩展）


## 2. 术语与核心概念

| 术语 | 说明 |
|------|------|
| **Prompt** | 用户输入的代码任务描述，在本项目中以 SWE-bench 实例的 Issue 描述作为主要输入 |
| **Codebase** | 待修改的目标代码库，来源于 SWE-bench 数据集中的仓库 |
| **Plan** | Agent 在代码生成前产出的方案文档，描述解决问题的思路、技术路线、模块修改范围和实现步骤 |
| **Patch** | 根据 Plan 生成的代码变更内容，以 Git Patch（diff）格式呈现，可直接应用到代码库中，对应 SWE-bench 评估框架的标准格式 |
| **Agent** | 执行任务的大语言模型智能体，在本项目中具体分为方案生成 Agent 和代码生成 Agent（可复用同一 Agent 但使用不同 Prompt） |
| **Trajectory** | Agent 在任务执行过程中的完整记录，包含推理步骤、行为序列、中间输出等信息 |
| **Optimization Feedback** | 用于优化 Plan 的信息集合，包括原始 Prompt、当前 Plan、生成 Plan 的 Agent 轨迹、生成的 Code、生成 Code 的 Agent 轨迹，以及可选的测试运行结果（stdout/stderr）和报错信息 |
| **Optimized Plan** | 基于 Optimization Feedback 经过反思/变异生成的新方案，目标是提升代码生成的测试通过率 |
| **GEPA** | Genetic-Pareto，一种基于自然语言反思的提示词/代码优化算法，通过“执行→反思→变异→评估→Pareto 选择”的循环实现迭代优化 |
| **ReAct** | Reasoning and Acting，Agent 的交互相应行为模式，包含推理（思考）和行动（调用工具/修改代码）交替进行的循环机制 |

## 3. 功能需求

### 3.1 核心功能：自动化方案生成与评估

#### FR-01：任务输入与系统初始化

| 属性 | 内容 |
|------|------|
| ID | FR-01 |
| 名称 | 任务输入与系统初始化 |
| 描述 | 系统读取配置文件，加载指定 SWE-bench 任务实例，初始化 Agent 运行环境 |
| 前置条件 | 已安装 SWE-bench 数据集、Docker 环境、KISS AI 框架和被调用的 LLM API（DeepSeek V4） |
| 输入 | SWE-bench 实例 ID（或实例列表）、配置文件路径 |
| 输出 | 待解决的代码库环境和 Issue 描述已被加载 |
| 验收标准 | 成功下载/加载目标仓库，Agent 能够访问代码库并执行工具调用 |

#### FR-02：代码库自主探索与方案生成

| 属性 | 内容 |
|------|------|
| ID | FR-02 |
| 名称 | Agent 自主探索与方案生成 |
| 描述 | Agent 根据 Issue 描述和配置文件中的生成 Prompt，在目标代码库中自主探索并生成方案（Plan） |
| 输入 | Issue 描述、代码库路径、方案生成 Prompt（从配置文件读取） |
| 输出 | Plan 文档（自然语言格式，包含问题分析、技术路线、修改方案和步骤） |
| 验收标准 | 生成的 Plan 应：1）能够被代码生成 Agent 理解；2）包含具体的文件修改范围信息 |
| 依赖 | Kiss AI Agent 框架、DeepSeek V4 API、KISS 框架中的 Agent 自主探索功能 |
| 备注 | Agent 的完整轨迹（Trajectory）需要被系统记录以供后续优化使用 |

#### FR-03：代码生成

| 属性 | 内容 |
|------|------|
| ID | FR-03 |
| 名称 | 根据方案生成代码 |
| 描述 | 代码生成 Agent 根据生成的 Plan 和配置文件中的代码生成 Prompt，生成符合 SWE-bench 格式的 Patch |
| 输入 | Plan 文档、Issue 描述、代码库上下文、代码生成 Prompt（从配置文件读取） |
| 输出 | Git Patch 格式的代码变更内容 |
| 验收标准 | 生成的 Patch 符合 SWE-bench 评估框架的 JSONL 格式要求，能够被直接评估 |
| 依赖 | 同 FR-02 |

#### FR-04：测试评估

| 属性 | 内容 |
|------|------|
| ID | FR-04 |
| 名称 | 代码测试评估 |
| 描述 | 在 SWE-bench 的 Docker 容器化环境中运行测试，评估生成的 Patch 是否解决了 Issue |
| 输入 | Patch 内容、SWE-bench 实例信息 |
| 输出 | 测试结果：通过/不通过，测试详细输出（stdout/stderr），通过率计算 |
| 验收标准 | 评估结果与 SWE-bench 官方评估工具的输出保持一致 |
| 依赖 | SWE-bench 评估框架 |


### 3.2 核心功能：方案迭代优化

#### FR-05：方案优化信息收集

| 属性 | 内容 |
|------|------|
| ID | FR-05 |
| 名称 | 方案优化信息收集 |
| 描述 | 系统在执行每一轮后收集用于优化首轮方案的信息集合，信息范围可通过参数配置 |
| 配置参数 | `optimization_info_level`：0=仅基础信息；1=包含测试运行结果和报错信息 |
| 输入 | 运行产生的各类输出 |
| 输出 | Optimization Feedback 数据结构（见 4.1） |
| 优化信息来源（基础） | 1）原始 Prompt（用户请求）；2）当前 Plan；3）生成 Plan 的 Agent Trajectory；4）生成的 Code；5）生成 Code 的 Agent Trajectory |
| 优化信息来源（可选） | 6）测试运行结果（stdout/stderr）；7）失败报错信息 |
| 验收标准 | 系统能够根据配置参数正确组装 Optimization Feedback |

#### FR-06：方案优化生成

| 属性 | 内容 |
|------|------|
| ID | FR-06 |
| 名称 | 方案优化生成 |
| 描述 | 基于 Optimization Feedback，利用优化算法（复用 GEPA）生成优化后的新方案。后序方案（Plan[i]）基于前序方案（Plan[i-1]）及其运行反馈迭代生成 |
| 输入 | Optimization Feedback、当前 Plan、优化 Prompt（从配置文件读取） |
| 输出 | 优化后的新 Plan（Plan[i]） |
| 优化算法 | 复用 KISS 框架中集成的 GEPA 优化模块，或直接引入 gepa-ai/gepa 库，按照 GEPA 的“执行→反思→评估→选择→变异”循环执行方案内容层面的迭代优化 |
| 验收标准 | 新 Plan 应能反映对前序方案失败原因的分析和相应改进尝试 |
| 依赖 | GEPA 优化算法 |
| 备注 | 优化过程中的 GEPA 反思记录应当被保存以供最终输出使用 |

#### FR-07：迭代循环控制

| 属性 | 内容 |
|------|------|
| ID | FR-07 |
| 名称 | 迭代循环控制 |
| 描述 | 控制系统执行多轮 plan-code-test 流程，按参数 n 生成指定数量的 Plan（n=1 时不产生后续优化，n>1 时循环优化产生 n 个 Plan） |
| 输入 | 目标 Plan 数量 n |
| 输出 | n 个 Plan，每个 Plan 对应的测试通过率，每次优化方案时的优化思路（即 GEPA 的“反思”输出） |
| 验收标准 | 1）若 n < 1 则系统报错退出；2）若 n == 1 则只执行单轮生成后退出；3）若 n > 1 则共执行 n 轮，Plan[1] 为首轮方案，Plan[2..n] 逐轮迭代优化前序方案，每轮 Plan[i] 均重新执行 FR-03 和 FR-04 |
| 迭代逻辑 | Plan[i]（i≥2）的优化输入包括 Plan[i-1] 执行产生的 Feedback（FR-05） |
| 备注 | 执行 n 轮指从首轮方案到 Plan[n] 生成的完整次数。Plan[1] 直接由 FR-02 生成，Plan[2..n] 由 FR-06 优化生成。每轮均执行 FR-03 和 FR-04 |


### 3.3 配置功能

#### FR-08：Agent Prompt 配置文件

| 属性 | 内容 |
|------|------|
| ID | FR-08 |
| 名称 | Agent Prompt 配置 |
| 描述 | 支持通过配置文件灵活修改三个核心 Agent 的 Prompt：方案生成 Prompt、代码生成 Prompt、方案优化 Prompt |
| 文件格式 | YAML 或 JSON |
| 配置项 | `plan_generation_prompt`（方案生成 Prompt）、`code_generation_prompt`（代码生成 Prompt）、`plan_optimization_prompt`（方案优化 Prompt） |
| 验收标准 | 用户可以在不修改代码的情况下，通过修改配置文件改变 Prompt 内容 |

#### FR-09：系统运行参数配置

| 属性 | 内容 |
|------|------|
| ID | FR-09 |
| 名称 | 系统运行参数配置 |
| 描述 | 支持配置文件配置系统运行的核心参数 |
| 配置项 | 1）`n`：目标 Plan 数量（整数，n≥1）；2）`optimization_info_level`：优化信息级别（0 或 1）；3）`model`：使用的 LLM 模型（deepseek-v4-flash 等）；4）其他与 KISS Agent 框架相关的运行时参数 |
| 验收标准 | 系统启动时自动加载配置文件，根据配置执行相应流程 |


### 3.4 输出功能

#### FR-10：结果输出

| 属性 | 内容 |
|------|------|
| ID | FR-10 |
| 名称 | 结果输出 |
| 描述 | 系统输出所有 Plan 及其对应的测试通过率、每次优化方案的思路 |
| 输出格式 | JSON 格式文件，包含：plan_id、plan_content、test_pass_rate、optimization_log（针对非首轮 Plan 记录在前一轮基础上优化时的 GEPA 反思文本） |
| 存储位置 | 通过配置文件指定输出目录 |
| 验收标准 | 输出文件结构清晰、易于解析和人工阅读 |


## 4. 数据模型

### 4.1 Optimization Feedback 数据结构

```json
{
  "original_prompt": "string",
  "current_plan": {
    "content": "string",
    "plan_id": "string"
  },
  "plan_agent_trajectory": "string",
  "generated_code": {
    "content": "string (patch format)",
    "code_id": "string"
  },
  "code_agent_trajectory": "string",
  "test_results": "string (optional, present if optimization_info_level=1)",
  "error_info": "string (optional, present if optimization_info_level=1 and test failed)"
}
```

### 4.2 Plan 数据结构

```json
{
  "plan_id": "string",
  "iteration_index": "integer (1-indexed)",
  "optimized_from": "string (plan_id of previous plan, null for plan 1)",
  "content": "string",
  "test_pass_rate": "float (0-1)",
  "trajectory_id": "string (reference to saved trajectory)",
  "generated_code_id": "string",
  "optimization_log": "string (reflection text from GEPA, null for plan 1)"
}
```

### 4.3 输出结果文件格式

```json
{
  "run_id": "string",
  "swe_bench_instance_id": "string",
  "model": "deepseek-v4-flash",
  "parameter_n": "integer",
  "optimization_info_level": "integer",
  "plans": [
    {
      "plan_id": "string",
      "iteration_index": 1,
      "test_pass_rate": 0.xx,
      "generated_code_path": "string",
      "optimization_log": null
    },
    {
      "plan_id": "string",
      "iteration_index": 2,
      "optimized_from": "plan_id_fk",
      "test_pass_rate": 0.xx,
      "generated_code_path": "string",
      "optimization_log": "string (GEPA reflection)"
    }
  ],
  "trajectory_directory": "string"
}
```


## 5. 非功能性需求

### 5.1 性能要求

| 需求 ID | 需求描述 | 指标 |
|---------|----------|------|
| NFR-01 | 单轮 plan-code-test 流程的执行时间（含 Agent 执行和测试评估）应控制在可接受范围内 | 因依赖 LLM API 响应时间和复杂任务，暂定每个 SWE-bench 实例 < 30 分钟 |
| NFR-02 | 迭代优化不应导致执行时间线性爆炸增长 | 每轮迭代使用 GEPA 优化算法，限定有限次数（≤50）的内循环 |
| NFR-03 | 支持并行执行多个 SWE-bench 实例（后续扩展） | 暂不要求 |

### 5.2 可靠性/稳定性要求

| 需求 ID | 需求描述 | 指标 |
|---------|----------|------|
| NFR-02 | 系统应具备错误恢复能力和异常处理机制 | 遇到执行异常时能够记录并继续执行后续实例或退出 |

### 5.3 可扩展性/可维护性要求

| 需求 ID | 需求描述 | 指标 |
|---------|----------|------|
| NFR-03 | 支持插拔式的 Agent 集成 | 基于 KISS 框架统一的 Agent 接口 |
| NFR-04 | 支持换用不同的 LLM 模型 | 通过 KISS 框架的模型抽象层配置实现 |
| NFR-05 | 代码模块化 | 方案生成、代码生成、评估、优化四个模块解耦 |

### 5.4 外部依赖限定条件

| 需求 ID | 需求描述 |
|---------|----------|
| NFR-06 | DeepSeek V4 API 必须可用，且按官方要求开通 DeepSeek V4-Flash 或 V4-Pro 资源 |
| NFR-07 | 系统运行环境需具备 Docker 以运行 SWE-bench 评估容器 |
| NFR-08 | Python 版本 ≥ 3.10 |
| NFR-09 | 保持 KISS AI 框架和 GEPA 库的原始代码不变，仅作为依赖引入或直接调用其 API |


## 6. 配置项规范

### 6.1 配置文件示例

```yaml
# system.yaml
system:
  n: 3                          # 目标 Plan 数量
  optimization_info_level: 1    # 优化信息级别: 0=基础, 1=包含测试结果
  model: deepseek-v4-flash      # 使用的 LLM 模型
  swe_bench_instance: astropy__astropy-14539  # SWE-bench 实例 ID
  output_dir: ./output          # 结果输出目录
  max_iterations: 3             # GEPA 优化每轮最大内循环次数

prompts:
  plan_generation_prompt: |
    你是一个专业的软件工程师，负责为以下问题设计解决方案方案...
  code_generation_prompt: |
    你是一个代码生成助手，根据以下方案生成代码...
  plan_optimization_prompt: |
    你是一个优化专家，根据以下 Feedback 改进方案...

kiss:
  max_trajectory_steps: 30
  trajectory_save_dir: ./trajectories
  agent_config:
    max_retries: 3
```

### 6.2 参数验证规则

| 参数 | 验证规则 | 错误处理 |
|------|----------|----------|
| n | 必须为整数且 ≥1 | n < 1 时系统报错退出 |
| optimization_info_level | 必须为 0 或 1 | 非法值时默认设为 0 并给出警告 |
| swe_bench_instance | 必须是 SWE-bench 数据集中的有效实例 ID | 无效时退出并提示可用实例列表 |
| model | 必须为 DeepSeek API 支持的模型标识 | 无效时提示可选模型并退出 |

## 8. 约束条件

| 约束类型 | 描述 |
|----------|------|
| 技术约束 | 核心 Agent 能力必须基于 KISS AI 框架实现；优化算法必须基于 GEPA 实现；测试评估必须复用 SWE-bench 官方的评估流程 |
| 模型约束 | LLM 模型限定为 DeepSeek V4-Flash（如后续有变化需同步更新配置文件） |
| 数据约束 | 数据集限定为 SWE-bench；代码环境在 Docker 容器中运行 |
| 开发约束 | 最小化开发原则，优先复用现有开源代码，不进行大规模重新实现 |
| 运行约束 | 需要持续的 DeepSeek API 调用权限和 Docker 环境 |


## 9. 风险与对策

| 风险项 | 风险描述 | 可能性 | 影响程度 | 缓解策略 |
|--------|----------|--------|----------|----------|
| R-01 | GEPA 算法集成后与 KISS Agent 框架的接口不兼容 | 中 | 高 | 提前准备独立的 Agent 接口适配层；准备备选方案：使用 KISSEvolve（KISS 框架自带的进化优化组件） |
| R-02 | DeepSeek V4 API 速率限制或成本超支 | 高 | 中 | 在配置文件中设置每轮的最大 Token 和 API 调用次数预算；启用 DeepSeek 提供的低延迟版本 V4-Flash 以降低 API 成本 |
| R-03 | SWE-bench 评估环境配置复杂或安装失败 | 中 | 中 | 使用官方预构建的 Docker 镜像了解运行时环境设置；开发时保留轻量级 Mock 评估模式进行初步测试 |
| R-04 | Agent 的自主探索可能因代码库过大而效率低下 | 中 | 中 | 在 Prompt 中引导 Agent 聚焦于 Issue 相关的目录或文件；设置 Agent 的最大步数限制 |
| R-05 | Agent 生成的 Plan 结构化程度不足，导致代码生成 Agent 无法有效解析 | 高 | 高 | 设计 Plan 模板规范（Markdown 格式，固定章节结构：问题分析、技术方案、文件列表、修改步骤）；在代码生成 Prompt 中明确说明如何解析 Plan 内容 |
| R-06 | GEPA 优化循环可能导致 prompt 内容膨胀超限 | 低 | 中 | 设置 GEPA 变异时最大长度限制；在 Prompt 压缩策略中确保方案内容长度在模型上下文窗口内 |


## 10. 验收标准

| 测试用例 ID | 测试描述 | 预期结果 |
|------------|----------|----------|
| TC-01 | 设置 n=1，运行一个 SWE-bench 实例 | 系统成功输出一个 Plan、对应的测试通过率，不执行优化流程 |
| TC-02 | 设置 n=3，运行一个 SWE-bench 实例 | 系统依次生成 Plan[1]、优化生成 Plan[2] 和 Plan[3]，每轮均进行代码生成和测试评估，输出三个 Plan 及其各自的测试通过率，每个后序 Plan 附带优化思路 |
| TC-03 | optimization_info_level=0 | 优化信息只包含基础内容（无测试结果）；仍能生成优化后的 Plan |
| TC-04 | optimization_info_level=1 | 优化信息包含测试运行结果和报错信息；能够生成体现测试反馈的 Plan |
| TC-05 | 修改配置文件中的 Prompt | 对应 Agent 的行为发生预期变化 |
| TC-06 | 设置 n=0 或 n=-1 | 系统报错退出 |
| TC-07 | 执行完整流程 | 输出结果文件符合规范中包含所有 Plan 和优化日志内容 |
